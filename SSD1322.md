# SSD1322 256×64 OLED — implementation notes (verified on hardware)

Portable reference for driving unbranded 256×64 4-grayscale OLED modules
(SSD1322 / SSD1322-class clones) from MicroPython on RP2040. Every fact here
was verified live during the bring-up in `proto2/bringup.py` (2026-10-13);
the low-level path is copied from [rdagger/micropython-ssd1322], whose demo
runs on this exact module at 25 MHz SPI.

> **Trust hierarchy:** rdagger driver + live board > datasheet excerpts >
> generic bring-up guides. A widely-circulated "SSD1322 clone bring-up"
> guide is SSD1306-contaminated and its sequence does NOT work on this
> module (see § Pitfalls).

## Hardware / wiring (verified config)

| Signal | Pico GP | Note |
|---|---|---|
| SCK  | GP18 | SPI0 (GP2/GP3 also work — same peripheral) |
| MOSI | GP19 | bus is **write-only**, no MISO |
| CS   | GP17 | one transaction per command |
| DC   | GP20 | 0 = command byte, 1 = data/params |
| RES  | GP21 | active-low |
| VCC  | 3V3(OUT) | not VBUS |

## SPI electrical (the #1 gotcha)

- **SPI MODE 0 (CPOL=0, CPHA=0)** — plain `machine.SPI` defaults. The
  popular "SSD1322 needs mode 3" claim is **wrong for this module**:
  mode 3 lets single command bytes through (panel responds to `0xA5`)
  but corrupts every multi-byte stream — the classic "init half-works,
  screen garbage" signature.
- Clock: 1 MHz is safe for everything; the chip handles **25 MHz** for
  framebuffer writes (rdagger's demo). Bring up slow, raise later.
- MSB first.

## Write path (the #2 gotcha)

Command **parameters are sent as DATA (DC=1)**, not as command bytes:

```python
def cmd(self, command, *args):
    self.dc.value(0); self.cs.value(0)
    self.spi.write(bytes((command,)))
    self.cs.value(1)
    if args:
        self.dc.value(1); self.cs.value(0)
        self.spi.write(bytes(args))
        self.cs.value(1)
```

One CS transaction per command. Do NOT bundle command+params with DC=0 —
this module mis-reads them.

## Reset

`RES low 50 ms → high → wait 100 ms` before any command.

## Init sequence (verified working)

```python
0xFD 0x12          # UNLOCK extended commands (do this first)
0xAE               # display off (sleep on)
0xB3 0x91          # front clock divider / osc freq
0xCA 0x3F          # multiplex 1/64  -- 0xCA, NOT 0xA8 (that's SSD1306)
0xA2 0x00          # display offset
0xA1 0x00          # display start line
0xA0 0x14 0x11     # remap (4-grayscale, COM scan dec) + dual COM line
0xB5 0x00          # GPIO: disable inputs
0xAB 0x01          # Function Selection: internal VDD regulator ON
0xB4 0xA0 0xFD     # enhancement A: external VSL + enhanced gray quality
0xC1 0x9F          # contrast current (0x00..0xFF)
0xC7 0x0F          # master current control (scale factor)
0xB9               # default linear gray-scale table
0xB1 0xE2          # phase length: 1st=5, 2nd=14 clocks
0xD1 0xA2 0x20     # enhancement B -- 0xD1, NOT 0xB2
0xBB 0x1F          # pre-charge voltage 0.60*VCC
0xB6 0x08          # 2nd pre-charge period
0xBE 0x07          # VCOMH 0.86*VCC
0xA6               # NORMAL display -- NOT 0xA4 (see Pitfalls)
0xA9               # partial display disable
0xAF               # display on (sleep off)
```

## Command reference (the ones that matter)

| Cmd | Params | Meaning |
|---|---|---|
| `0xFD` | `0x12` / `0x16` | unlock / lock extended commands |
| `0xAE` / `0xAF` | — | display off (sleep) / on (wake) |
| `0xA4` | — | **ENTIRE DISPLAY OFF** (not "resume from RAM"!) |
| `0xA5` | — | entire display ON (test mode, ignores RAM) |
| `0xA6` / `0xA7` | — | normal / inverse (this is "resume from RAM") |
| `0x15` | start, end | column address window — in **4-grayscale units** |
| `0x75` | start, end | row address window (0..63) |
| `0x5C` | — | start writing to display RAM (then DC=1 stream) |
| `0x5D` | — | read RAM (needs MISO; unused) |
| `0xA0` | `0x14 0x11` | remap + dual COM line |
| `0xA1` | line | display start line |
| `0xA2` | offset | display offset |
| `0xA8`/`0xA9` | — | partial display enable/disable |
| `0xAB` | `0x01` | function selection: internal VDD regulator |
| `0xB1` | `0xE2` | phase length |
| `0xB3` | `0x91` | front clock divider / osc frequency |
| `0xB4` | `0xA0 0xFD` | display enhancement A (VSL + gray quality) |
| `0xB5` | `0x00` | GPIO |
| `0xB6` | `0x08` | 2nd pre-charge period |
| `0xB8` | 16 bytes | custom gray-scale table |
| `0xB9` | — | default linear gray table |
| `0xBB` | `0x1F` | pre-charge voltage |
| `0xBE` | `0x07` | VCOMH deselect voltage |
| `0xC1` | `0x00..0xFF` | contrast current (main brightness knob) |
| `0xC7` | `0x0F` | master current control scale |
| `0xCA` | `0x3F` | multiplex ratio (1/64) |
| `0xD1` | `0xA2 0x20` | display enhancement B |

Extended commands (B1, B3, B4, B5, B6, BB, BE, C1, C7, CA, D1, FD-locked
family) require the `0xFD 0x12` unlock first.

## RAM addressing + framebuffer (the #3 gotcha)

- 4-grayscale mode: **one column address = 4 pixels = 2 RAM bytes**.
  256 px wide → column addresses **0..63**, not 0..255.
- These modules wire the panel to **segment 112 → column address 28**.
  Correct window: `0x15 28 91` (offset 28 + 64 addresses).
  Wrong window = image lands in unconnected channels → garbage in a
  fraction of the screen, rest black.
- Rows: `0x75 0 63`.
- Framebuffer: 256×64 @ 4bpp = **8192 bytes** packed (not 2048 — that's
  the 1bpp size; not 16384).
- Nibble order (GS4_HMSB): **high nibble = lower/even pixel** of each
  byte pair.
- Present = `0x15 28 91`, `0x75 0 63`, `0x5C`, then the 8192-byte buffer
  as one DC=1 stream.

```python
def present(self):
    c0, c1 = 28, 28 + self.width // 4 - 1   # 28..91 for 256 px
    self.cmd(0x15, c0, c1)
    self.cmd(0x75, 0x00, self.height - 1)
    self.cmd(0x5C)
    self.dc.value(1); self.cs.value(0)
    self.spi.write(self.fb)                 # 8192 bytes, one burst
    self.cs.value(1)
```

MicroPython has a native packed format that matches exactly:
`framebuf.FrameBuffer(buf, 256, 64, framebuf.GS4_HMSB)` — use it instead
of hand-rolled `pixel()` math.

## Pitfalls catalog (each one cost a live debug cycle)

| Symptom | Cause | Fix |
|---|---|---|
| Panel lights fully on `0xA5` but RAM writes are garbage | SPI **mode 3** (guide claim) vs actual **mode 0** | SPI defaults |
| Params seem ignored (unlock/window do nothing) | params sent with DC=0 | send params as **data (DC=1)** |
| Image occupies one quarter of the screen, rest black | column window `0x15 0x00 0xFF` | `0x15 28 91` (4-px addresses + segment-112 offset) |
| Panel goes black after a "resume from RAM" command and never recovers | `0xA4` on SSD1322 = **entire display OFF** | use `0xA6` for normal |
| Multiplex/power commands ignored | guide used `0xA8` (SSD1306) | multiplex is `0xCA` |
| Enhancement settings ignored | guide used `0xB2` | enhancement B is `0xD1` |
| Faint panel | VDD regulator off | `0xAB 0x01` (internal VDD) |
| "2048-byte framebuffer" | guide's buffer math | 8192 bytes at 4bpp |

## Bring-up ladder (what to run when a new module arrives)

1. `0xA5` → whole panel must light (proves bus+power+interface; no
   addressing involved). `0xA6` → dark again.
2. RAM blank (`fill(0)` + present) → stays dark.
3. Single 16×16 block at x=0/64/128/192, then y=48, then x=0 again —
   localizes width, column mapping, row mapping, and "does a second
   write still land".
4. Checkerboard (packing), gradient (gray LUT), `0xC1` sweep (extended
   commands + lock state).
